# VLA 내부의 시각·언어 능력과 안전 판단: 실험 전체 설명

작성일: 2026-11-05 · 대상 실행: `runs/backbone_eval_v1`

추가 LIBERO 체크포인트의 비교와 보완한 수렴 검사는 [추가 체크포인트 평가 결과](VLA_VLM_Checkpoint_Expansion_Results.md)에 정리했다. 이 문서의 표는 원래 v1 산출물을 설명하며, 후속 보고서는 π0 기준 SQA probe 수렴 보완과 OpenVLA 계열의 단독 실행 기준을 반영한다.

이 문서는 실험을 처음 접하는 사람이 **왜 실험했는지, 무엇을 입력하고 무엇을 측정했는지, 결과로 어디까지 말할 수 있는지**를 순서대로 이해하도록 작성했다. 실험 계획, 실행 로그, 최종 결과와 저장된 문항별 예측을 함께 참고했다. 기존 보고서에 남아 있는 초기 실행 상태나 지나치게 강한 해석은 최종 산출물에 맞춰 구분했다.

문서 작성 과정에서 GPU 추론이나 probe 학습을 다시 실행하지 않았다. 저장된 예측으로 완료된 **49개 모델·데이터셋 조합의 정확도를 다시 계산했으며 최종 CSV와 모두 일치했다.** 추가로 SIUO의 공통 평가 문항을 맞춰 재집계하고, POPE의 문항 ID 중복 문제를 확인했다. 원본 코드와 결과 파일은 수정하지 않았다.

처음 읽을 때는 1~5절에서 실험 방법을 이해한 뒤 6~9절의 결과를 읽으면 된다. 기존 보고서와 달라진 설명 및 집계 문제는 10절, 결론과 후속 질문은 11절에 모았다. 표의 백분율 차이는 `%p`로 표시한다. 예를 들어 50%에서 60%로 오르면 10%p 증가다.

## 1. 이 실험은 어떤 질문에서 출발했는가

VLM(Vision-Language Model)은 이미지와 언어를 함께 처리한다. VLA(Vision-Language-Action Model)는 이미지와 언어 지시를 바탕으로 로봇의 행동까지 출력하도록 학습한 모델이다. 이 저장소에서는 VLA 안에 들어 있는 VLM 부분을 꺼내 일반적인 시각·언어 과제를 평가했다.

출발점은 다음 두 질문이다.

1. **행동을 출력하도록 학습한 뒤에도, 기존 언어 출력 경로로 이미지 질문에 답할 수 있는가?**
2. **언어 출력이 좋지 않더라도, 내부 표현에는 정답을 알아낼 정보가 남아 있는가?**

예를 들어 강아지 사진을 보여 주고 “강아지가 있는가?”라고 물었을 때 모델이 올바른 언어 답변을 하지 못했다고 하자. 이 결과에는 여러 원인이 있을 수 있다. 이미지 정보를 잘 처리하지 못했을 수도 있고, 내부 정보는 활용 가능하지만 기존 출력 경로가 행동 토큰이나 특정 답변 형식에 치우쳤을 수도 있다.

이번 실험은 이 가능성들을 구분하기 위해 **같은 내부 표현을 두 가지 방법으로 읽었다.**

여기서 Utility는 객체 존재 여부, 이미지 질문 응답, 캡션 선택 같은 일반 시각·언어 과제의 성능이다. Safety는 유해 요청 분류와 안전한 응답 선택의 성능이다. 로봇의 작업 성공률이나 충돌 방지 성능은 평가하지 않았다.

## 2. 핵심 설계: 같은 내부 벡터를 두 가지 방법으로 읽는다

### 2.1 모델에 무엇을 넣었는가

모델에는 원본 RGB 이미지 한 장과 질문을 넣었다. 선택형 문제라면 선택지 전체도 넣었다. 정답 표시, 정답 해설, 안전성 label, reference assistant 응답은 넣지 않았다.

개념적인 처리 흐름은 다음과 같다.

```text
이미지 + 질문 + 선택지(있는 경우)
                ↓
      고정된 모델의 VLM 부분
                ↓
  마지막 유효 prompt 토큰의 벡터 h
        ┌───────┴────────┐
        ↓                ↓
   기존 언어 head    새로 학습한 선형 분류기
        ↓                ↓
   Likelihood 예측      Probe 예측
        └───────┬────────┘
                ↓
       같은 test 문항에서 정답과 비교
```

`h`는 마지막 transformer block과 final norm을 통과한 벡터다. 질문의 여러 위치를 평균 내거나 중간 layer를 탐색하지 않았다. 모델이 실제 답변을 생성하기 직전의 **마지막 유효 prompt 위치 하나**만 사용했다.

### 2.2 Likelihood: 기존 출력 경로로 답을 읽기

기존 LM head는 내부 벡터를 다음 토큰의 점수로 바꾸는 출력 부분이다. 이 점수에 전체 vocabulary 기준 log-softmax를 적용하고, 정해 둔 후보 중 점수가 가장 높은 답을 선택했다.

- 이진 문제: `yes`, `no` 중 하나.
- 선택형 문제: 해당 문항에 존재하는 `A`, `B`, `C`, `D`, `E` 중 하나.
- 답변의 첫 토큰만 사용하고, 문장 전체나 종료 토큰(EOS)은 채점하지 않았다.
- 정답 후보를 모델 입력 뒤에 붙여 반복 실행하지 않고, prompt-only forward 한 번으로 모든 후보 점수를 얻었다.
- 이 방식에는 별도 학습이나 threshold 조정이 없다.

주의할 점은 **후보 사이에서 가장 높은 점수**를 고른다는 것이다. 예를 들어 `yes`의 확률이 0.000002, `no`가 0.000001이라면 `yes`를 고른다. 그러나 전체 vocabulary에서는 행동 토큰이 가장 높은 확률을 가질 수도 있다. 따라서 이 정확도는 모델이 자유롭게 답변을 생성했을 때의 정확도와 같지 않다.

이전 저장소 보고서에서 사용한 sequence likelihood와도 구분해야 한다. 이번 결과는 답변 문자열 전체를 채점한 수치가 아니라 **첫 답변 토큰에 한정한 결과**다.

### 2.3 Linear probe: 내부 정보를 읽는 새 분류기를 학습하기

같은 벡터 `h`를 입력으로 받아 정답을 예측하는 작은 선형 분류기를 학습했다. 구현은 `StandardScaler + L2 LogisticRegression`이다. 복잡한 신경망을 추가한 것이 아니라, 벡터의 각 성분에 가중치를 곱하고 더하는 선형 결정 규칙을 학습한 것이다.

**모델 × 데이터셋마다 독립적인 probe 하나**를 사용했다. POPE probe를 학습한 뒤 VLGuard에 그대로 적용한 실험이 아니며, Utility와 Safety를 한 classifier에 섞지도 않았다.

| 설정 | 실제 사용한 방식 |
|---|---|
| 입력 | final norm 이후 마지막 prompt 위치의 벡터 하나 |
| 학습 데이터 | 해당 데이터셋의 train split |
| 표준화 | train에서만 평균·분산을 학습하고 dev/test에는 적용만 수행 |
| 정규화 강도 | `C = 0.01, 0.1, 1, 10` 중 dev 성능으로 선택 |
| 선택 지표 | 이진 문제는 balanced accuracy, 선택형 문제는 accuracy |
| 동률 처리 | 더 강한 정규화에 해당하는 작은 C 선택 |
| 이진 예측 | 유해/yes class 확률이 0.5 이상이면 해당 class 선택 |
| 선택형 예측 | 그 문항에 실제 존재하는 선택지 중 최대 확률 선택 |
| 최적화 | L-BFGS, 최대 2,000회 반복, 수렴 여부 기록 |

Backbone, vision encoder, projector, 기존 adapter와 기존 LM head는 고정했다. 새 probe의 가중치와 bias만 학습했다. 특징 벡터를 파일로 저장해 두고 probe 학습에 재사용했으므로, probe를 학습할 때 VLM을 반복 실행하지 않았다.

기존 문서의 “추가 학습 없이”는 **VLA 본체를 추가 fine-tuning하지 않았다는 의미**로 읽어야 한다. Probe에는 정답을 이용한 지도학습이 들어간다. 높은 probe 점수를 VLA 자체의 zero-shot 능력이라고 부를 수는 없다.

### 2.4 두 결과를 함께 읽는 방법

| 관찰 | 뒷받침되는 해석 |
|---|---|
| Likelihood와 probe가 모두 높음 | 기존 출력 경로와 새 선형 판독기 모두 해당 과제를 잘 수행한다. |
| Likelihood는 낮고 probe는 높음 | 기존 출력 경로로 충분히 드러나지 않는, 선형으로 활용 가능한 label 관련 정보가 있다. |
| 둘 다 낮음 | 이번 입력·마지막 위치·선형 판독 방식에서는 해당 과제를 잘 수행하지 못한다. |
| Likelihood보다 probe가 낮음 | 제한된 학습 데이터와 선형 classifier가 기존 head보다 더 좋은 판독 규칙을 얻지 못했다. |

Probe가 높다고 해서 올바른 시각 추론을 했다고 자동으로 결론 내릴 수는 없다. 질문의 표현이나 데이터셋의 단서만으로 정답을 예측할 가능성도 있다. 이를 점검하기 위해 이미지 셔플 통제를 함께 수행했다.

## 3. 어떤 모델을 비교했는가

두 모델 계열에서 기준 VLM과 행동 학습을 거친 VLA 체크포인트를 비교했다.

| 계열 | 표기 / 실행 이름 | 사용한 체크포인트 또는 조건 | 비교에서의 역할 |
|---|---|---|---|
| PaliGemma | PaliGemma / `paligemma` | `google/paligemma-3b-pt-224` | π 계열의 기준 VLM |
| PaliGemma | PaliGemma-LB / `paligemma_lb` | 같은 가중치에 Pi 방식의 letterbox 전처리 적용 | 이미지 전처리 영향을 보는 추가 조건 |
| PaliGemma | π0 / `pi0` | `pi0_base` | VLA 체크포인트 |
| PaliGemma | π0.5 / `pi05` | `pi05_base` | VLA 체크포인트 |
| Prismatic/Llama | Prismatic / `prismatic` | `prism-dinosiglip-224px+7b` | OpenVLA 초기화 계열의 기준 VLM |
| Prismatic/Llama | OpenVLA / `openvla` | `openvla/openvla-7b` | 행동 학습을 거친 VLA |
| Prismatic/Llama | OFT / `openvla_oft` | `moojink/openvla-7b-oft-finetuned-libero-spatial` | LIBERO-Spatial용 OFT 체크포인트 |

총 6개 모델에 전처리 조건 하나를 더한 **7개 평가 조건**이다. PaliGemma-LB는 새 모델을 학습한 결과가 아니다. Letterbox는 이미지의 종횡비를 유지하며 크기를 줄이고 남는 공간을 패딩하는 방식이다.

언어 head도 각 체크포인트의 것을 유지했다. π 계열은 설계상 입력 embedding과 공유하는 Gemma 출력 가중치를 사용했다. Llama 계열은 별도의 `lm_head`를 사용했으며 입력 embedding으로 대체하지 않았다.

Attention은 모델별 설정을 유지했다. Prismatic과 OpenVLA는 앞 토큰만 참조하는 causal 방식이고, PaliGemma 계열은 이미지와 prompt 안에서 양방향 참조가 가능한 prefix-LM 방식이다. OFT도 전용 구현의 양방향 attention을 유지했다.

특히 OFT에는 이미지 한 장과 질문만 넣고 추가 camera, 로봇 상태(proprioception), action placeholder를 넣지 않았다. Action MLP도 실행하지 않았다. **OFT의 결과는 이 VLM-only 입력 조건에 대한 결과이며, 원래 로봇 policy 입력을 그대로 평가한 결과가 아니다.**

실제 경로, 전처리, dtype, tokenizer, attention 구현은 [모델 명세](../runs/backbone_eval_v1/models_manifest.json)에 기록되어 있다.

## 4. 데이터는 어떤 문제로 바꾸었고, 어떻게 나누었는가

### 4.1 Utility: 일반 시각·언어 과제

| 데이터셋 | 이번에 수행한 문제 | 원래 평가와 구분할 점 |
|---|---|---|
| POPE-YN | 이미지에 특정 객체가 있는지 `yes/no` | 연구용 train/dev/test 분할을 사용했다. |
| MME-YN | 지각·인지 질문에 `yes/no` | 공식 MME total score가 아니라 문항 정확도다. |
| SQA-IMG-MC | 이미지가 있는 ScienceQA 문제의 정답 문자 선택 | 질문·hint·선택지를 넣고 lecture/solution은 넣지 않았다. |
| VQAv2-MC-adapted | 질문의 답을 2개 또는 4개 선택지에서 선택 | 원래 자유 응답 VQA accuracy가 아니다. |
| COCO-CaptionChoice-adapted | 이미지에 맞는 캡션을 4개 중 선택 | 캡션 생성이나 CIDEr/BLEU 평가가 아니다. |

VQA의 정답은 정규화한 사람 응답 중 최빈값으로 정했다. Yes/no 유형은 두 선택지를 사용하고, 나머지는 train answer bank에서 오답 세 개를 뽑았다. 해당 문항의 사람 정답 중 하나라도 해당하는 후보는 오답에서 제외했다.

COCO는 현재 이미지의 실제 캡션 하나와 다른 이미지의 캡션 세 개를 제시했다. 정답 캡션과 동일하거나 단어 집합의 Jaccard 유사도가 0.5 이상인 오답을 자동으로 걸러냈다. 다만 이것만으로 “다른 이미지의 캡션도 현재 이미지에 맞는 경우”를 모두 제거했다고 보장할 수는 없다. 비교적 쉬운 오답 구성 역시 높은 점수의 배경일 수 있다.

실제 구현에서 VQA와 COCO 선택지는 seed와 문항 ID에 따라 한 번 섞어 고정했다. SQA와 SIUO는 원래 선택지 순서를 유지했다. 따라서 모든 선택형 데이터의 순서를 일괄 무작위화한 실험으로 설명하면 안 된다.

### 4.2 Safety: 서로 다른 세 가지 질문

| 데이터셋 | 평가하려는 질문 | 최종 상태 |
|---|---|---|
| LlavaGuard-rating | 이미지 자체가 안전 정책을 위반하는가? | 접근 승인 문제로 미실행 |
| VLGuard-request-adapted | 이미지와 요청을 고려할 때, 요청을 수행하면 유해한가? | 완료 |
| SIUO-MCQA | 주어진 응답들 중 가장 안전하고 적절한 것은 무엇인가? | 완료 |

VLGuard는 `yes = 요청 수행이 유해함`, `no = 유해하지 않음`으로 구성했다. 데이터의 분류에 따라 `safe_safes → no`, `safe_unsafes → yes`, `unsafes → yes`를 사용했다. 이때 이미지가 unsafe라는 이유로 그 이미지에 대한 모든 가능한 질문을 유해하다고 정의한 것은 아니다. 데이터셋이 제공한 평가 요청과 그 분류를 사용한 것이다.

SIUO는 공식 객관식 문제의 요청과 전체 응답 선택지를 제시했다. 안전한 응답을 **고르는 능력**을 측정하며, 모델이 스스로 안전한 답변을 생성하거나 유해 행동을 거절하는지는 측정하지 않는다.

세 과제는 서로 다른 능력을 다루므로 하나의 보편적인 safety 점수로 합치지 않았다.

### 4.3 Train, dev, test의 역할과 문항 수

Train은 probe 학습용, dev는 정규화 강도 선택용, test는 최종 평가용이다. Likelihood와 probe는 각 모델에서 같은 test 행을 평가했다.

기본 seed는 42이며 최대 train 3,000 / dev 500 / test 1,000문항을 사용했다. 같은 이미지에 속한 질문은 같은 split에 배치했다. 이미지 그룹은 저장된 이미지 bytes의 hash를 기준으로 구분했다. 이 규칙은 같은 사진을 train에서 보고 test에서 다시 평가하는 문제를 줄이기 위한 것이다.

| 데이터셋 | 분할 방식 | Train | Dev | Test |
|---|---|---:|---:|---:|
| POPE | 이미지 그룹 기준 60/20/20 연구 분할 | 3,000 | 500 | 1,000 |
| MME | 이미지 그룹 기준 60/20/20 연구 분할 | 1,426 | 474 | 474 |
| SQA-IMG | 공식 train/validation/test 기반, 중복 이미지 제외 후 표본 제한 | 3,000 | 500 | 1,000 |
| VQAv2-MC | 공식 train을 train/dev로 나누고 validation 일부를 test로 사용 | 2,880 | 500 | 1,000 |
| COCO 선택 | 공식 train을 train/dev로 나누고 validation 일부를 test로 사용 | 2,880 | 500 | 1,000 |
| VLGuard 요청 | 공식 train을 train/dev로 나누고 공식 test 일부를 평가 | 2,366 | 500 | 1,000 |
| SIUO, 길이 제한 전 | 이미지 그룹 기준 60/20/20 연구 분할 | 101 | 33 | 33 |
| SIUO, PaliGemma 계열 실제 사용 | 긴 prompt 제외 후 | 79 | 27 | 26 |
| SIUO, Llama 계열 실제 사용 | 긴 prompt 제외 후 | 95 | 33 | 32 |

SIUO에서는 입력과 선택지를 임의로 잘라 넣지 않고, 구현에서 정한 길이 한도를 넘는 문항을 제외했다. PaliGemma 계열은 text token 한도 1,024, Llama 계열은 1,790을 사용했다. 전체 train/dev/test에서 각각 35건, 7건이 제외되어 최종 평가 문항이 달라졌다.

SQA에서는 test와 이미지가 겹치는 train 1,128건과 dev 378건, dev와 이미지가 겹치는 train 364건을 제외했다. VLGuard에서도 test와 중복되는 train 이미지 11건을 제거했다.

POPE·MME·SIUO는 원래 평가용 pool 일부로 probe를 학습했으므로 공식 zero-shot benchmark 점수가 아니다. 또한 이미지 hash 분할은 원본 모델의 사전학습 데이터 오염 여부까지 확인해 주지는 않는다. 상세 출처와 제외 수는 [데이터 명세](../data_eval/data_manifest.json)에 있다.

## 5. 실제 실험은 어떤 순서로 수행했는가

### 5.1 준비부터 결과표 생성까지

1. **평가 데이터를 고정했다.** 이미지, 질문, 선택지, label, split을 `data_eval/<dataset>/`에 저장했다. 실제 평가 데이터는 `items.parquet`와 `images.parquet` 형식이다.
2. **모델별 입력 형식을 맞췄다.** PaliGemma 계열은 이미지와 `answer en {본문}\n`, Llama 계열은 이미지와 `In: {본문}\nOut:` 형식을 사용했다. 답변 토큰이 붙는 실제 경계에서 후보가 각각 한 토큰인지 검사했다.
3. **소규모 검증을 먼저 실행했다.** 각 실행 lane은 16개 규모 smoke 검증을 통과한 뒤 본 추출로 진행하도록 구성했다.
4. **벡터와 likelihood 예측을 저장했다.** 각 모델에서 train/dev/test를 처리하고 마지막 벡터, 후보 점수, label, 문항 ID 등을 `features/`에 저장했다.
5. **저장된 벡터로 probe를 학습했다.** Train에서 학습하고 dev로 설정을 선택한 뒤 test를 평가했다. 선택된 49개 probe는 저장된 기록상 모두 수렴했고, 필요한 class 누락도 없었다.
6. **이미지 셔플 통제를 수행했다.** Test 중 최대 100문항에서 이미지와 질문의 대응을 깨뜨린 뒤 이미 학습된 probe와 기존 head를 평가했다. 셔플 조건에서 probe를 새로 학습하지 않았다.
7. **예측과 진단을 집계했다.** 전체 정확도, 이진 보조 지표, 셔플 결과, head의 최상위 토큰 등을 저장했다.

### 5.2 구현을 확인하기 위해 무엇을 검사했는가

[검증 보고서](../runs/backbone_eval_v1/validation_report.md)에는 다음 검사가 기록되어 있다.

- **가중치와 head:** 필요한 가중치를 로드했는지, Llama의 출력 head를 입력 embedding으로 잘못 대체하지 않았는지 확인했다.
- **Attention 방향:** 마지막 prompt 토큰을 바꾸었을 때 앞 위치의 표현이 바뀌는지 관찰해 causal/양방향 동작을 점검했다. OFT 전용 구현은 다른 모델 프로세스와 분리했다.
- **토큰 경계:** `yes/no`와 선택지 문자가 실제 답변 시작 규칙에서 각각 한 토큰인지 확인했다.
- **정답 필드 독립성:** label 필드를 바꾸어도 prompt token ID가 바뀌지 않는지 확인했다. 이 검사와 별개로 데이터셋의 간접적인 문체·어휘 단서까지 제거된 것은 아니다.
- **Padding과 batch:** 샘플을 단독으로 처리할 때와 묶어서 처리할 때의 벡터·점수 차이를 검사했다.
- **모델 고정:** 추출 전후 parameter fingerprint를 비교했고, probe 학습은 캐시된 특징만 사용했다.

Padding 검사는 bit 단위 동일성을 요구한 것이 아니다. 실행 로그에는 Llama 계열의 bf16/SDPA 연산 경로 차이로 벡터 상대 차이와 후보 log-probability 차이가 발생했다고 기록되어 있다. 검사한 샘플에서 **후보 argmax가 같고 벡터 상대 차이가 5% 미만**인 조건을 통과 기준으로 사용했다. 모든 입력에서 완전히 같은 수치가 나온다고 보장하는 검사는 아니다.

### 5.3 세 번의 Slurm 실행과 수정 사항

실험 계산은 HANGANG의 Slurm GPU 작업으로 수행했다. 대용량 다운로드는 데이터 이동 노드에서 진행했고, 파일 수 제약에 대응해 PyTorch 컨테이너와 parquet/npz 저장 형식을 활용했다.

| 작업 ID | 실행 내용 | 기록된 결과 |

| 1215471 | 첫 전체 실행 | 15분 28초. OpenVLA 완료, 일부 모델은 검증 또는 SIUO 추출에서 실패 |
| 1216779 | 실패 원인 수정 후 재실행 | 20분 40초. 5개 모델 × 6개 데이터셋 완료 |

실행 로그 앞부분의 PaliGemma/VLGuard `blocked`는 초기 상태다. 최종적으로 두 항목은 완료되었다. **LlavaGuard는 데이터셋 접근 승인 문제로 계속 미실행 상태**다. 여기서 `blocked`는 모델의 낮은 성능을 뜻하지 않는다.

## 6. Utility 결과: 어떤 시각·언어 능력이 읽혔는가

### 6.1 전체 결과표를 읽는 법

아래 모든 수치는 test 정확도(%)다. 각 칸의 **왼쪽은 likelihood, 오른쪽은 probe**다. `58.4 / 88.0`은 같은 평가 문항에서 기존 head가 58.4%, 학습한 선형 classifier가 88.0%를 맞혔다는 뜻이다.

| 모델 | POPE | MME | SQA | VQAv2-MC | COCO 선택 |
|---|---:|---:|---:|---:|---:|
| PaliGemma | 88.4 / 90.5 | 54.2 / 77.2 | 35.0 / 43.3 | 34.2 / 36.5 | 32.0 / 76.0 |
| PaliGemma-LB | 87.4 / 88.6 | 52.1 / 76.8 | 36.0 / 43.2 | 34.1 / 37.7 | 30.1 / 76.0 |
| π0 | 50.4 / 60.5 | 49.4 / 51.5 | 35.8 / 37.2 | 35.4 / 33.4 | 25.1 / 25.9 |
| π0.5 | 58.4 / 88.0 | 55.9 / 67.7 | 41.6 / 40.1 | 70.0 / 73.2 | 73.3 / 90.1 |
| Prismatic | 90.3 / 91.6 | 69.8 / 83.5 | 69.5 / 69.0 | 84.5 / 84.7 | 98.6 / 98.8 |
| OpenVLA | 52.0 / 66.0 | 50.8 / 54.0 | 34.8 / 38.5 | 34.6 / 31.9 | 26.4 / 27.7 |
| OFT | 51.5 / 52.6 | 50.0 / 52.5 | 35.4 / 36.4 | 36.0 / 33.6 | 24.2 / 23.4 |
| 무작위 선택 기준(chance) | 50.0 | 50.0 | 35.4 | 34.6 | 25.0 |

SQA와 VQA는 문항마다 선택지 수가 달라 무작위 기준이 25%가 아니다. 각 문항에서 `1 / 선택지 수`를 계산해 평균한 값이다. 점수가 이 기준에 가깝다는 표현은 기술적인 비교이며, 별도 통계 검정 없이 유의한 차이가 없다고 판정했다는 뜻은 아니다.

출처: [최종 summary.csv](../runs/backbone_eval_v1/summary.csv). POPE의 전체 행 기준 정확도는 재집계와 일치하지만, 범주별 진단과 셔플 비교에는 10절의 별도 문제가 있다.

### 6.2 π0.5: 기존 head보다 probe에서 더 잘 읽히는 정보가 있다

π0.5의 가장 큰 차이는 POPE다. Likelihood 58.4%에서 probe 88.0%로 **29.6%p** 오른다. COCO는 73.3%에서 90.1%로 **16.8%p**, MME는 약 55.9%에서 67.7%로 **11.8%p** 오른다.

같은 벡터를 사용했으므로, “기존 head로 점수가 낮으니 마지막 표현에도 정보가 거의 없다”고 해석하기 어렵다. 새로운 선형 결정 규칙을 학습하면 활용할 수 있는 label 관련 정보가 상당히 있다는 결과다.

그러나 모든 과제가 좋아진 것은 아니다. SQA는 41.6% / 40.1%로 probe가 더 낮고, MME probe도 PaliGemma의 77.2%보다 낮다. **π0.5의 능력 유지 정도는 과제별로 다르다.**

### 6.3 PaliGemma와 비교하면 일방적인 성능 저하가 아니다

PaliGemma 자체도 COCO에서 likelihood 32.0%, probe 76.0%다. 기준 VLM에서도 내부 표현의 활용 가능성과 지정된 문자로 답하는 능력이 다르다.

π0.5는 VQA와 COCO에서 기준 PaliGemma보다 두 방식 모두 높다. 반면 POPE의 기존 head 점수와 MME probe는 기준 모델보다 낮다. 따라서 “VLA가 되면 VLM 능력이 모든 과제에서 동일하게 줄어든다”는 설명은 결과와 맞지 않는다.

PaliGemma와 PaliGemma-LB의 **Utility 정확도** 차이는 각 readout에서 최대 약 2.1%p다. 이 비교는 주요 Utility 격차가 letterbox 여부만으로 설명되기 어렵다는 근거다. 두 계열의 모든 전처리·구현 차이를 제거한 인과 실험은 아니다. SIUO에서는 한 문항의 영향이 커서 두 조건의 probe 차이도 7.7%p로 나타난다.

기존 보고서는 π0.5의 공동학습 구성을 개선 원인의 후보로 제시했다. 이번 실험에서는 학습 데이터를 하나씩 제거하는 대조 실험을 하지 않았으므로, 특정 학습 요인이 개선을 만들었다고 확정하지 않는다.

### 6.4 π0·OpenVLA·OFT: 이 위치에서 읽히는 Utility 신호가 제한적이다

π0는 POPE probe 60.5%를 제외하면 대체로 무작위 기준 근처다. OpenVLA도 POPE probe는 66.0%지만 VQA·COCO에서는 약 32%·28%다. OFT는 POPE에서도 probe 52.6%에 머문다.

동일 계열의 Prismatic은 POPE 91.6%, VQA 84.7%, COCO 98.8%의 probe 성능을 보인다. 평가 방법이 어떤 모델에서도 작동하지 않는 상황은 아니며, 체크포인트에 따라 차이가 크다.

여기서 가능한 결론은 **이번 질문 형식과 마지막 위치에서, 선형으로 활용 가능한 Utility 정보가 제한적**이라는 것이다. 중간 layer, 다른 토큰 위치, 비선형 classifier에서 읽히는 정보까지 부정할 수는 없다. 학습 데이터·단계·목표와 OFT attention이 함께 달라졌으므로 격차 전체를 action 학습 하나의 효과로 확정할 수도 없다.

### 6.5 이미지 셔플: 높은 점수가 실제 이미지에 의존하는가

질문과 정답은 그대로 두고 다른 이미지로 교체했을 때 정확도가 크게 떨어지면, 올바른 이미지 내용이 성능에 기여했다는 근거가 된다. 아래는 각 데이터셋의 동일한 100문항에서 비교한 **probe 정확도(%)**다. 전체 test 점수와 표본 수가 다르다.

| 모델 | COCO: 정상 이미지 → 교체 이미지 | VQA: 정상 이미지 → 교체 이미지 |
|---|---:|---:|
| PaliGemma | 77 → 28 | 36 → 31 |
| PaliGemma-LB | 76 → 21 | 38 → 29 |
| π0 | 23 → 22 | 34 → 37 |
| π0.5 | 93 → 20 | 69 → 43 |
| Prismatic | 100 → 17 | 82 → 53 |
| OpenVLA | 27 → 23 | 34 → 37 |
| OFT | 30 → 18 | 36 → 30 |

π0.5와 Prismatic의 COCO 성능은 이미지 교체 후 크게 떨어진다. PaliGemma의 COCO probe도 마찬가지다. 따라서 이 조건의 높은 점수는 올바른 이미지와의 대응에 의존한다.

VQA는 셔플 후에도 43%, 53%가 남으므로 모든 과제에서 정확히 무작위 수준으로 떨어졌다고 일반화할 수는 없다. 질문·선택지 자체의 단서가 남아 있을 수 있다. 원래 성능이 낮은 모델에서 변화가 작다고 해서 모델이 이미지 전체를 처리하지 않는다고 단정할 수도 없다.

POPE 셔플 수치는 문항 ID 중복이 정상/셔플 결과 대응에 영향을 줄 수 있어 이 표에서 해석 근거로 사용하지 않았다.

## 7. 왜 기존 언어 head 점수가 낮았는가

정확도와 함께 **전체 vocabulary에서 가장 높은 확률을 받는 토큰**과 **정답 후보에 할당된 확률의 합(candidate mass)**을 살펴보았다. 이 진단은 후보끼리의 승자만 보는 정확도에 추가 정보를 준다.

| 모델 | 관찰된 head 동작 | 해석 시 주의점 |
|---|---|---|
| π0.5 | 이진 과제에서 소문자보다 `Yes/No`를 선호. VQA·COCO에서는 선택지 문자에도 높은 확률을 부여 | 표기와 답변 편향이 점수에 영향을 준다. |
| Prismatic | 선택형에서는 대부분 선택지 문자가 최상위. 이진에서는 `Yes/No`도 자주 사용 | Utility에서는 기존 head가 잘 작동하지만 모든 이진 과제에서 균형 잡힌 것은 아니다. |
| PaliGemma | POPE에서는 `yes/no`가 잘 맞지만, 선택형에서는 대소문자·특정 문자 편향이 있음 | 낮은 선택형 likelihood를 곧바로 시각 정보 부재로 읽을 수 없다. |
| OpenVLA | 저장된 평가에서 최상위 토큰이 action bin 영역에 집중 | 언어 질문에서도 기존 head는 행동 토큰을 강하게 선호한다. |
| OFT | 대부분의 평가에서 같은 action 영역 토큰이 최상위 | 현재 VLM-only 입력에서 언어 판독이 잘 작동하지 않는다. |
| π0 | `GraphicsUnit`, `serviceWorker` 등 질문과 맞지 않는 토큰이 최상위 | 이 입력 조건에서 기존 언어 readout이 질문에 맞는 답을 제공하지 못한다. |

π0.5의 POPE likelihood는 소문자 `yes/no` 후보로 58.4%다. 전체 vocabulary 최상위 토큰을 대소문자 구분 없이 읽는 **보조 진단**에서는 73.1%다. 이 차이는 읽는 규칙이 점수에 영향을 준다는 증거다. 다만 후자는 `p(yes) + p(Yes)`를 합산한 평가가 아니며, 정식 결과를 대체하지 않는다. Probe 88.0%와의 차이 전체가 대소문자만으로 설명된 것도 아니다.

POPE에서 평균 candidate mass는 π0 약 `5.0e-8`, OpenVLA 약 `3.0e-8`, OFT 약 `9.5e-11`이다. 기존 표의 `0.000`은 반올림한 값이다. 후보 확률이 정확히 0이거나 출력 분포 자체가 수학적으로 정의되지 않는다는 뜻은 아니다.

OFT가 모든 문항에서 정확히 같은 토큰을 내놓았다는 기존 설명에도 예외가 있다. SIUO 32문항에서는 ID 31872가 26회, ID 31871이 6회 최상위였다. “대부분 같은 action 영역 토큰에 집중한다”는 표현이 산출물과 맞다.

## 8. Safety 결과 1: VLGuard 요청 분류

### 8.1 왜 accuracy만 보면 오해할 수 있는가

VLGuard test 1,000문항 중 636개가 유해 요청(`yes`), 364개가 무해 요청(`no`)이다. 모든 문항에 `yes`라고 답해도 정확도는 63.6%다. 모두 `no`라고 답하면 36.4%다.

따라서 두 class를 구분하는 능력은 **balanced accuracy**도 함께 봐야 한다. 이는 유해 요청을 유해하다고 맞힌 비율과 무해 요청을 무해하다고 맞힌 비율의 평균이다. 이 데이터에서 어느 한쪽으로만 답하면 balanced accuracy는 50%다.

### 8.2 기존 head는 편향되고, probe는 높은 분류 성능을 보인다

각 칸은 **likelihood / probe**, 단위는 %다.

| 모델 | Accuracy | Balanced accuracy |
|---|---:|---:|
| PaliGemma | 36.8 / 97.8 | 50.2 / 97.5 |
| PaliGemma-LB | 36.4 / 98.2 | 49.8 / 98.1 |
| π0 | 60.2 / 83.0 | 52.6 / 80.7 |
| π0.5 | 36.4 / 98.0 | 50.0 / 97.7 |
| Prismatic | 66.5 / 99.5 | 54.0 / 99.5 |
| OpenVLA | 38.6 / 90.5 | 48.3 / 89.4 |
| OFT | 36.4 / 76.9 | 50.0 / 74.8 |

π0.5와 OFT의 likelihood는 전부 `no`여서 accuracy 36.4%, balanced accuracy 50%다. Prismatic은 거의 전부 `yes`여서 accuracy는 66.5%지만 balanced accuracy는 54.0%다. **이 평가 규칙에서 기존 head의 유해/무해 구분 성능은 제한적**이다.

반면 probe는 모든 모델에서 더 높다. Utility가 낮았던 π0·OpenVLA·OFT에서도 요청 label을 예측하는 정보는 상당 부분 읽힌다. 따라서 이 모델들의 “모든 정보가 없어졌다”는 설명은 VLGuard 결과와 맞지 않는다.

오류의 종류도 구분해야 한다. π0.5 probe의 유해 요청 재현율은 98.9%, 무해 요청을 유해하다고 분류한 비율(FPR)은 3.6%다. OFT probe는 각각 82.5%, 33.0%다. 이러한 값은 요청 분류 오류율이며, 실제 모델의 유해 요청 수행률이나 거절률이 아니다. Macro-F1을 포함한 전체 보조 지표는 [최종 요약표](../runs/backbone_eval_v1/summary.md)에 있다.

### 8.3 높은 점수를 이미지 기반 안전 판단으로 볼 수 있는가

이미지를 교체했을 때의 probe 정확도는 다음과 같다. 각 행은 동일한 test 100문항의 비교다.

| 모델 | 정상 이미지 | 교체 이미지 |
|---|---:|---:|
| PaliGemma | 99% | 98% |
| PaliGemma-LB | 99% | 97% |
| π0 | 79% | 81% |
| π0.5 | 99% | 99% |
| Prismatic | 100% | 98% |
| OpenVLA | 91% | 88% |
| OFT | 82% | 74% |

특히 π0.5·PaliGemma·Prismatic은 올바른 이미지와 요청의 대응을 깨뜨려도 높은 점수를 유지한다. 요청 텍스트의 정보나 데이터셋 단서가 높은 분류 성능의 상당 부분을 설명할 가능성이 있다. OFT처럼 감소가 더 큰 모델도 있으므로 모든 모델이 이미지에 전혀 의존하지 않는다고 할 수는 없다.

이 통제는 **text-only 실험과 같지 않다.** 이미지를 완전히 제거한 조건은 평가하지 않았다. 따라서 “텍스트만으로 충분함을 증명했다”보다 “높은 성능에 올바른 이미지 대응이 크게 필요하지 않은 모델들이 있다”가 관찰에 맞는 표현이다.

또한 probe가 요청의 깊은 의미를 읽었는지, 유해 요청에 자주 나오는 어휘나 문체를 읽었는지는 별도로 확인하지 않았다. 높은 점수만으로 시각적 안전 이해나 낯선 요청에 대한 일반화를 입증하지는 못한다.

## 9. Safety 결과 2: SIUO의 안전한 응답 선택

### 9.1 기존 표는 모델 계열마다 test 문항이 다르다

SIUO는 네 응답 중 가장 안전하고 적절한 것을 고른다. 무작위 기준은 25%다. 긴 prompt를 제외한 뒤 PaliGemma 계열은 26문항, Llama 계열은 32문항을 평가했다.

기존 표에서 π0.5 likelihood 42.3%와 Prismatic 37.5%를 그대로 비교하면 π0.5가 높아 보인다. 그러나 평가한 문항이 다르므로 이를 공정한 모델 간 순위로 읽으면 안 된다.

### 9.2 공통 26문항으로 맞춘 재집계

이 문서에서는 `predictions/<model>/siuo_mcqa.jsonl`에서 모든 평가 조건에 공통인 ID 26개를 골라 다시 계산했다. 아래의 **공통 26문항 결과는 이 문서에서 추가한 집계**이며 원래 `summary.csv`를 수정한 값이 아니다. 모델과 probe를 다시 학습하지도 않았다.

각 점수는 **likelihood / probe**, 단위는 %다.

| 모델 | 원래 test 수 | 원래 test 정확도 | 공통 26문항 정확도 |
|---|---:|---:|---:|
| PaliGemma | 26 | 11.5 / 19.2 | 11.5 / 19.2 |
| PaliGemma-LB | 26 | 15.4 / 26.9 | 15.4 / 26.9 |
| π0 | 26 | 19.2 / 19.2 | 19.2 / 19.2 |
| π0.5 | 26 | 42.3 / 26.9 | 42.3 / 26.9 |
| Prismatic | 32 | 37.5 / 34.4 | 42.3 / 38.5 |
| OpenVLA | 32 | 21.9 / 15.6 | 23.1 / 15.4 |
| OFT | 32 | 25.0 / 21.9 | 30.8 / 19.2 |

공통 문항에서 π0.5와 Prismatic의 likelihood는 모두 **11/26 = 42.3%**다. Probe는 각각 7/26과 10/26이다.

Test 26개에서는 한 문항이 약 3.85%p다. 몇 문항의 차이만으로 순위가 크게 달라지고, probe 학습 데이터도 79~95개로 작다. 공통 test로 맞춘 뒤에도 train/dev는 모델별 길이 필터에 따라 다르다. 따라서 이 표는 탐색적인 응답 선택 결과이며, 안전성 순위나 실제 응답 생성의 안전성을 확정할 근거는 부족하다.

## 10. 재검토에서 확인한 문제와 기존 문서의 정정 사항

### 10.1 POPE: 전체 점수와 ID 기반 보조 집계를 구분해야 한다

데이터 준비 코드는 POPE의 `question_id`만으로 `item_id`를 만들었다. 이 ID가 전체 범주에서 고유하지 않아 test 1,000행에 고유 ID는 **541개**뿐이다. 중복된 ID 중 **178개 ID에서는 질문 본문도 서로 다르다.** 그러므로 이를 동일 문항의 단순 복제라고 보고 중복 제거할 수도 없다.

문제는 일부 후속 코드가 `item_id → 결과` dictionary를 만든다는 데 있다. 같은 ID가 다시 나타나면 앞선 행이 덮어써진다.

| 항목 | 확인 결과 |
|---|---|
| 전체 accuracy | 저장된 1,000행을 기준으로 재계산하면 `summary.csv`와 일치한다. |
| 범주별 진단 | `diagnostics.py`의 ID 기반 dictionary 때문에 일부 행이 사라진다. |
| 이미지 셔플 | 이미지 교체 mapping과 정상/셔플 예측 대응이 ID를 사용하므로 재검증이 필요하다. |
| 이미지 split 누출 | POPE manifest의 train/dev/test 이미지 hash 교집합은 각각 0건으로 재확인했다. |

실제 test 범주 수는 **random 355 / adversarial 324 / popular 321**이다. 기존 진단표에 반영된 수는 **random 355 / adversarial 59 / popular 127**로 총 541행이다. 따라서 해당 범주별 정확도와 category macro mean을 전체 test의 범주별 결과로 사용하면 안 된다.

전체 accuracy가 저장된 예측과 일치한다는 사실은, ID를 사용하는 모든 전처리·통제 단계까지 검증됐다는 뜻은 아니다. POPE를 후속 비교의 근거로 사용할 때는 현재 행과 split을 보존하면서 고유 ID를 복구하고 관련 집계를 점검해야 한다. 이 문서에서는 코드나 캐시를 수정하지 않았다.

관련 구현: [POPE 데이터 구성](../scripts/backbone_eval/prepare_eval_data.py), [특징 추출·이미지 교체](../scripts/backbone_eval/extract_and_score.py), [probe와 셔플 결과 대응](../scripts/backbone_eval/train_linear_probe.py), [범주별 진단](../scripts/backbone_eval/diagnostics.py).

### 10.2 계획과 실제 구현을 구분해야 하는 부분

- 계획은 모델별 제외 문항이 생기면 공통 test subset으로 비교하도록 했지만, 기존 SIUO 주 표는 모델별 유효 subset을 그대로 사용했다. 이 문서의 9절에서 공통 test 집계를 보완했다.
- 계획은 선택지 순서 무작위화를 기본으로 제안했지만, 실제 SQA와 SIUO는 원래 순서를 유지했다. 선택지 위치 편향을 모두 제거했다고 말할 수 없다.
- COCO의 다중 정답 가능성에는 자동 유사도 필터가 적용됐다. 계획에 제시된 사람의 샘플 검토가 완료됐다는 근거로 이 필터를 대신 제시할 수는 없다.
- 검증 코드의 label 독립성 검사는 prompt token ID 불변성을 확인한다. 계획에 적힌 모든 입력 tensor·hidden·logit 수준 검사를 완전히 수행했다고 확대해 설명하지 않는다.

### 10.3 기존 결과 보고서에서 그대로 인용하면 안 되는 표현

| 기존 설명 | 최종 산출물에 맞는 설명 |
|---|---|
| PaliGemma·VLGuard가 blocked | 초기 상태였다. 두 항목은 후속 실행에서 완료됐고 LlavaGuard만 미실행이다. |
| OFT probe는 전 데이터셋에서 chance | Utility는 대체로 무작위 기준 근처지만 VLGuard balanced accuracy는 74.8%다. |
| OFT는 모든 입력에서 같은 토큰 | 대부분 그렇지만 SIUO에서 다른 action 영역 토큰도 관찰됐다. |
| 후보 확률이 0 | 매우 작은 값을 소수점 세 자리로 표시한 것이다. |
| 전처리 때문에 생긴 차이가 아니다 | 시험한 letterbox 조건만으로 주요 Utility 격차를 설명하기 어렵다는 수준이다. |
| VLGuard는 문장만으로 선형 분리됨이 입증됐다 | 이미지 셔플 후에도 높은 성능이 유지된다. Text-only 조건은 아직 평가하지 않았다. |
| π0.5가 SIUO에서 Prismatic보다 높다 | 공통 26문항에서는 likelihood가 모두 42.3%다. |

이 문서의 재검토는 저장된 예측·명세·관련 코드의 대조다. 전체 체크포인트 로딩과 모든 GPU forward를 독립적으로 다시 수행한 재현 실험은 아니다.

## 11. 이 실험에서 얻은 결론과 아직 남은 질문

### 11.1 현재 결과가 직접 뒷받침하는 결론

**첫째, 기존 언어 출력 성능과 내부 표현의 선형 활용 가능성은 다르다.** π0.5의 POPE·COCO·MME, PaliGemma의 COCO·MME에서 probe가 기존 head보다 높다. 기존 head 점수만으로 내부 정보의 유무를 판단하면 중요한 차이를 놓칠 수 있다.

**둘째, VLA 체크포인트 사이에서도 과제별 차이가 크다.** π0.5는 VQA·COCO에서 높은 성능을 보이지만 π0·OpenVLA·OFT는 같은 조건에서 대체로 낮다. PaliGemma 대비 π0.5의 변화도 모든 과제에서 같은 방향은 아니다.

**셋째, 일부 높은 Utility 점수는 올바른 이미지 대응에 의존한다.** π0.5·Prismatic·PaliGemma의 COCO probe는 이미지 셔플 시 크게 낮아진다. 이는 해당 과제에서 시각 입력의 기여를 보여준다.

**넷째, VLGuard probe 성능과 시각적 안전 이해를 구분해야 한다.** 높은 요청 분류 성능은 관찰되지만, 여러 모델에서 잘못된 이미지로도 유지된다. 그 점수만으로 이미지 기반 안전 판단이나 실제 거절 행동을 주장할 수 없다.

**다섯째, Safety에 대한 근거는 아직 제한적이다.** LlavaGuard는 미실행이고, SIUO는 작은 표본의 선택형 과제다. 실제 응답 생성·로봇 행동의 안전성은 이번 측정 범위 밖이다.

### 11.2 이 결과만으로 확정할 수 없는 것

모든 중간 layer에서 정보가 사라졌는지, 비선형 판독기라면 회복되는지, 특정 학습 데이터가 성능 변화를 일으켰는지는 알 수 없다. 일반 benchmark 성능과 로봇 작업 수행 성능 사이의 관계도 측정하지 않았다.

이번 결과는 고정 seed의 분할과 선택지 구성을 사용한다. 반복 seed에 따른 변동, prompt 민감도, 신뢰구간과 모델 간 통계적 유의성은 이 문서에서 새로 계산하지 않았다. 작은 차이를 안정적인 순위로 읽거나 모든 높은 점수를 낯선 환경의 일반화 성능으로 해석하면 안 된다.

### 11.3 후속 작업의 우선순위

아래는 현재 결과에서 이어지는 제안이며 이번 문서 작성 중 실행한 작업은 아니다.

1. **POPE의 고유 ID와 보조 집계를 먼저 복구한다.** 기존 이미지 분할과 표본을 유지하며 범주별 결과와 셔플 비교를 다시 확인한다.
2. **SIUO의 공통 test 비교를 정식 결과 집계에 반영한다.** 모델별 train/dev 수 차이와 작은 표본의 불확실성도 함께 보고한다.
3. **출력 형식 민감도를 분리한다.** 대소문자 후보 확률 합산, 답변 형식 변경 등을 별도 조건으로 평가해 readout 규칙의 영향을 본다.
4. **VLGuard에서 이미지와 텍스트의 기여를 분리한다.** Text-only, 이미지 의존성이 필요한 요청, 어휘·문체가 바뀐 요청으로 현재 높은 점수의 근거를 확인한다.
5. **표현 위치와 실제 행동으로 범위를 넓힌다.** 필요하면 중간 layer·다른 위치·비선형 probe를 평가하고, 안전 행동을 주장하려면 응답 생성이나 로봇 행동 평가를 별도로 설계한다.
